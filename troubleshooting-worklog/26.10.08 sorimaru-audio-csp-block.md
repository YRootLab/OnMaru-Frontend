# 소리마루 API는 정상인데 음원이 재생되지 않음

- 날짜: 2026-10-08
- 관련 PR: [#365](https://github.com/YRootLab/OnMaru-Frontend/pull/365)

## 문제 상황과 실패 증상

소리마루에서 이야기 목록과 상세 정보는 나타났지만 재생 버튼을 눌러도 소리가 나지 않았다. 브라우저의 `HTMLAudioElement.play()`는 `NotSupportedError: Failed to load because no supported source was found`로 거부됐고, 미디어 요소의 오류는 `MEDIA_ELEMENT_ERROR: Media load rejected by URL safety check`였다. 재생 상태는 다시 `false`로 돌아갔다.

## 확인한 경로와 증거

1. `src/features/sorimaru-audio/infrastructure/sorimaruHttpRepository.ts`의 `getStoryDetail()`은 이야기 ID와 언어를 받아 `GET /api/v1/odii/stories/{storyId}`를 호출하고, 응답을 `mapStoryDetail()`로 변환한다. 운영 API는 `audioUrl`을 포함한 상세 응답을 `200`으로 반환했다.
2. 응답의 `audioUrl`은 `https://sfj608538-sfj608538.ktcdn.co.kr/file/audio/...mp3`였다. 운영 목록에서 확인한 첫 12개 음원 URL은 모두 범위 요청에 `206 audio/mpeg`로 응답했다. 따라서 URL 자체가 사라졌거나 서버가 MP3를 제공하지 않는 문제는 아니었다.
3. `src/features/sorimaru-audio/store/useSorimaruAudioStore.ts`의 `selectAndLoadStory()`는 상세 응답을 `currentStory`에 넣고, 재생 의도일 때 `isPlaying`을 `true`로 만든다. `src/features/sorimaru-audio/hooks/useSorimaruAudioPlayer.ts`는 `currentStory.audioUrl`을 `Audio` 객체의 `src`로 지정하고 `play()`를 호출한다. 이 호출까지 실행됐지만 브라우저가 음원 로드를 거부했다.
4. `src/middleware.ts`의 `middleware()`는 요청마다 Content Security Policy(CSP)를 만들어 응답 헤더에 넣는다. 수정 전 `media-src 'self' blob:`는 우리 사이트의 미디어와 `blob:` URL만 허용했다. 외부 음원 호스트가 빠져 있었으므로 브라우저가 재생 요청을 차단했다.

`git blame`과 파일 이력을 확인하면 이 제한은 2026-10-05의 프론트엔드 보안 변경 `5507ad6`에서 도입됐다. 소리마루 재생 흐름이 새로 고장 난 시점은 이 CSP 적용과 일치한다. 변경 작성자의 개인 실수 여부가 아니라, 새 보안 정책에 기존 음원 호스트가 누락된 통합 문제로 분류했다.

CDN은 MP3 파일을 제공하는 외부 서버이고, CSP의 `media-src`는 페이지에서 음원·영상 로드를 허용할 서버를 지정한다. 목록·상세 API가 정상이어도 이 규칙에서 음원 서버를 허용하지 않으면 재생할 수 없다.

## 검토한 선택지와 판단

- 플레이어의 `play()` 호출 순서 변경: 호출은 이미 실행되고 있었으므로 원인을 해결하지 못한다.
- `media-src https:`처럼 모든 HTTPS 미디어 허용: 동작은 가능하지만 허용 범위가 필요 이상으로 넓다.
- 음원을 우리 서버로 프록시: 추가 서버 트래픽과 구현이 필요하고, 현재 문제에는 과하다.
- 실제 MP3 호스트만 `media-src`에 추가: 원인을 직접 해결하면서 기존 정책의 제한을 유지한다.

## 최종 결정과 해결

`src/middleware.ts`의 `media-src`에 `https://sfj608538-sfj608538.ktcdn.co.kr`만 추가했다. 이제 상세 API가 반환한 해당 호스트의 MP3를 브라우저가 로드할 수 있다. `src/middleware.test.ts`에는 해당 호스트를 허용하고 `https:` 전체를 포괄 허용하지 않는 회귀 테스트를 추가했다. 플레이어 동작과 UI는 변경하지 않았다.

## 결과와 남은 확인

- 수정 전 로컬 브라우저에서 위 미디어 오류를 재현했다.
- 수정 후 같은 음원이 브라우저에서 `206 audio/mpeg`로 로드되고 `readyState: 4`, `playing: true`, `error: null`이 됐다.
- `npx vitest run src/middleware.test.ts`와 `npx tsc --noEmit`이 통과했다.
- PR이 `develop`에 병합되면 미리보기 환경에서 실제 재생을 다시 확인해야 한다.
- 조사 시점의 `staging-api.onmaru.site`는 별도로 `503`을 반환했다. 이는 운영 API의 음원 재생 차단 원인과 구분해서 봐야 한다.
