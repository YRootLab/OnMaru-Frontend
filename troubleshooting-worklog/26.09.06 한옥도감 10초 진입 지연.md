# 한옥도감 10초 진입 지연과 빈 화면 수정

## 날짜
2026-09-06

## 문제 상황
소리마루 또는 랜딩에서 한옥도감(`/hanok`)으로 이동할 때 화면 전환이 약 10초 멈추고, 열린 뒤에도 일부 섹션이 사라지거나 비어 보였다. 사용자는 한옥 페이지의 배경을 흰색으로 변경해 달라고 함께 요청했다.

## 오류명 또는 실패 증상
- 개발 서버: `GET /hanok 200 in 10.1s (next.js: 52ms, application-code: 10.0s)`.
- 연속 요청도 `10.0s`로 같아 최초 compile 문제가 아니었다.
- 외부 TourAPI의 encoded/raw service key URL을 각각 직접 호출했지만 둘 다 3.5초 안에 응답하지 못하고 `TimeoutError`가 발생했다.
- timeout 뒤 페이지는 HTTP 200이지만 `meta.total=0`, `villages=[]`였다.
- 빈 데이터 때문에 이달의 한옥은 `null`, 도감은 empty state, 지도는 marker 없음 상태가 됐다.

## 기존 구조나 방식의 한계
- `src/app/hanok/page.tsx` 서버 컴포넌트가 `fetchRealtimeHanoks()`를 완료해야만 `HanokArchive`를 반환했다.
- archive service는 네 카테고리 요청을 병렬 실행했지만 `Promise.allSettled()`가 모든 결과를 기다려 가장 긴 10초 timeout이 route TTFB가 됐다.
- `TourApiClient`는 10초 signal을 사용하고 두 service-key URL을 순회한다. 외부 API가 무응답이면 데이터 실패가 페이지 렌더 실패와 직접 결합됐다.
- 네 요청이 모두 실패하면 fallback 없이 빈 배열을 정상 결과처럼 반환했다.
- `/hanok/loading.tsx`도 없어 기다리는 동안 route feedback이 없었다. loading UI만 추가해도 10초와 빈 데이터 문제는 해결되지 않는다.

## 관련 코드 맥락

### `src/app/hanok/page.tsx`
- 이전 책임: 서버 렌더 중 실시간 API 완료를 기다리고 결과를 client archive에 전달했다.
- 변경 책임: 동기 `HANOK_ARCHIVE_FALLBACK`을 즉시 전달한다.
- 결과: 외부 network가 route response의 선행 조건이 아니다.

### `src/hanok/data/hanokArchiveFallback.ts`
- 입력: 마지막 정상 수집본 `src/data/hanokVillages.fallback.json`.
- 출력: HTTPS image URL과 현재 `VillageMeta` 계약으로 정규화한 `{ villages, meta }`.
- 핵심 분기: `decodeHanokArchivePayload()`는 비어 있거나 meta가 없는 live payload를 거부해 정상 snapshot이 빈 응답으로 지워지지 않게 한다.

### `src/hanok/HanokArchive.tsx`
- 입력: 서버가 전달한 snapshot villages/meta.
- 출력: 기존 이달의 한옥, 도감, 스테이, 지도 UI.
- 핵심 분기: hydration 뒤 `/api/tourapi`를 요청하고 5초 내 유효한 non-empty payload가 올 때만 state를 교체한다. 실패 시 snapshot을 유지한다.
- 배경: route Root와 body Global style만 `#ffffff`로 변경했다.

### `src/hanok/services/hanokArchive.service.ts`
- 네 TourAPI 카테고리 호출과 raw item 변환을 담당한다.
- request signal을 외부에서 받아 네 호출에 전달할 수 있게 해 client navigation이 끝나거나 refresh budget이 지나면 작업을 중단할 수 있다.

## 검토한 선택지
1. TourAPI timeout을 10초에서 1초로만 줄인다. 반려. 지연은 줄지만 빈 도감과 API 결합은 남는다.
2. `/hanok/loading.tsx`만 추가한다. 반려. 기다림을 가릴 뿐 TTFB와 빈 데이터는 그대로다.
3. 서버 cache만 추가한다. 반려. cache가 없는 첫 요청과 API 장애 중 갱신에는 여전히 10초가 필요하다.
4. snapshot-first 렌더 후 client background refresh를 수행한다. 채택.

## 판단 기준
- 외부 API 장애가 `/hanok` HTML 응답을 막지 않아야 한다.
- API URL, 인증, payload가 바뀌어도 UI는 snapshot으로 동작해야 한다.
- 실시간 데이터가 정상일 때는 기존 화면을 갱신할 수 있어야 한다.
- 기존 섹션 순서, typography, animation, 카드 UI는 바꾸지 않는다.
- 요청한 페이지 배경만 흰색으로 변경한다.

## 최종 결정
서버 route는 정적 snapshot을 즉시 렌더하고 실시간 API는 hydration 이후의 비차단 갱신으로 분리했다. 빈 응답은 실패로 처리해 snapshot을 유지한다.

## 해결 방식
1. 이전 정상 수집본 17개를 `src/data/hanokVillages.fallback.json`으로 복원했다.
2. fallback 정규화와 live payload decoder를 별도 모듈로 추가했다.
3. 페이지 서버 컴포넌트에서 `await fetchRealtimeHanoks()`를 제거했다.
4. `HanokArchive`에 abort 가능한 background refresh를 추가했다.
5. API route의 request signal을 archive service와 TourAPI client까지 전달했다.
6. 한옥 Root와 route body 배경을 `#ffffff`로 변경했다.
