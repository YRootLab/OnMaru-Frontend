# 소리마루 첫 진입 직후 스크롤 병목 진단과 완화

## 날짜
2026-09-06

## 문제 상황
메인 랜딩(`/`)에 처음 접속한 뒤 소리마루(`/odii`)로 이동하면, 재진입이나 새로고침 때보다 초반 스크롤이 느리게 느껴졌다. UI, 색, typography, 페이지 flow, 정상 motion 값은 유지하면서 첫 진입에만 겹치는 작업을 찾아야 했다.

## 오류명 또는 실패 증상
- `/odii` 최초 요청은 개발 서버에서 `158ms`였지만, 진입 직후 브라우저가 `fillOpacity`를 `undefined`에서 `0.92` 또는 `1`로 애니메이션한다는 Framer Motion 경고를 SVG path 수만큼 반복했다.
- Sound Constellation은 화면 아래쪽 섹션인데도 `rootMargin: 700px` 때문에 일반 데스크톱 첫 viewport에서 활성화되어 `/api/odii` 요청, 지도 path animation, 목록 구성이 초기 스크롤과 겹쳤다.
- 랜딩은 `/anchae.glb`를 로드한다. 파일은 `11,995,928B`이며 107 nodes, 107 meshes, 16 WebP textures, 371 accessors를 포함한다. 사용자가 모델 로드 직후 바로 이동하면 네트워크와 GLTF parse가 후보 부하가 될 수 있다.
- 자동화 브라우저와 Playwright/Puppeteer가 없어 Performance trace와 desktop/mobile visual regression은 수행하지 못했다.

## 기존 구조나 방식의 한계
- `useOneShotViewportActivation` 자체는 한 번만 활성화되지만 Sound Constellation의 700px 선행 margin이 너무 넓어 lazy loading이 사실상 초기 loading이 됐다.
- 지도 path의 `initial`에는 `fill`만 있고 `animate`에는 `fillOpacity`와 `filter`가 추가되어 Motion이 정의되지 않은 시작값을 보간했다.
- 랜딩의 세 모듈에는 같은 `MODEL_URL`에 대한 `useGLTF.preload()`가 총 5회 있었다. R3F cache가 중복 network fetch는 합치지만, module evaluation 시점의 preload는 React lifecycle 밖에서 시작되고 GLTF loader에는 진행 중 요청을 취소하는 API가 없다.
- 동시에 `<Canvas>`와 `HanokScene`이 첫 렌더부터 mount되므로 preload 호출만 제거해도 정상 랜딩의 모델 load/parse는 즉시 시작한다. 실측 없이 Canvas mount를 늦추면 기존 한옥 등장 timing과 fallback 노출이 바뀔 수 있다.

## 관련 코드 맥락

### `src/shared/hooks/useOneShotViewportActivation.ts`
- 책임: IntersectionObserver를 이용해 아직 보지 않은 무거운 섹션을 한 번만 활성화한다.
- 입력: `rootMargin`, `threshold`, observer 대상 ref.
- 출력: `isActivated`와 대상 ref.
- 핵심 분기: reduced motion 여부와 무관하게 data activation은 동일하며, intersect 후 observer를 해제하고 final state를 유지한다.

### `src/features/odii-audio/components/SoundConstellationSection.tsx`
- 책임: 전국 소리 지도, 지역 선택, 지역별 story 목록을 렌더한다.
- 입력: 초기 story와 선택 지역.
- 출력: SVG 지도 및 lazy API 결과 기반 목록.
- 핵심 분기: viewport activation 전에는 API를 호출하지 않고 기존 skeleton geometry를 유지한다. 활성화 후에만 지역 데이터를 요청한다.

### `src/features/odii-audio/components/soundConstellationMotion.ts`
- 책임: 지도 path의 완전한 visual state를 순수 함수로 계산한다.
- 입력: `selected`, `hasSelection`.
- 출력: 항상 `fill`, `fillOpacity`, `filter`가 모두 있는 `TargetAndTransition`.
- 핵심 분기: 선택 path, 비선택 path, 아직 선택이 없는 path를 각각 기존 색·opacity·filter 값으로 반환한다.

### `src/LandingExperience.jsx`와 한옥 모델 컴포넌트
- 책임: 2000vh 랜딩 scroll story, Lenis, R3F Canvas, 한옥 GLB scene을 운영한다.
- 입력: document scroll progress와 scene store 상태.
- 출력: 기존 카메라, 조명, 한옥 조립 animation.
- 핵심 분기: Canvas opacity는 progress `0.06~0.12`에서 나타나지만 Canvas와 GLB hook 자체는 progress 0부터 mount된다. cleanup은 Lenis와 requestAnimationFrame을 정상 해제한다.

## 검토한 선택지
1. Sound Constellation의 API activation을 실제 viewport 진입까지 미룬다. 채택. 초기 화면의 UI와 skeleton 크기는 그대로이고, 보이지 않는 data 작업만 늦춘다.
2. 지도 path의 `initial`과 `animate`에 동일한 완전 상태를 공급한다. 채택. 선택/hover transition의 `0.4s` duration, easing, 색, opacity, filter는 유지하면서 undefined 보간만 제거한다.
3. 랜딩 Canvas 또는 GLB load를 idle/scroll threshold까지 늦춘다. 보류. 12MB parse 경쟁은 줄일 수 있지만 기존 loader 종료와 한옥 fade-in 사이의 timing 및 fallback 노출이 바뀔 위험이 있다.
4. GLB를 Draco/Meshopt로 재압축하거나 texture 해상도를 낮춘다. 보류. 현재 파일에는 geometry 압축 extension이 없지만, 재가공은 모델 외형과 decode 특성을 바꾸므로 visual 비교 환경 없이 적용하지 않는다.
5. 5개의 `useGLTF.preload()`만 제거한다. 보류. module side effect는 줄지만 현재 Canvas가 즉시 같은 resource를 요청하므로 체감 개선을 보장하지 못하고, 핵심 병목에 대한 수정으로 과장될 수 있다.

## 판단 기준
- 첫 `/odii` viewport의 main-thread/network 경쟁을 실제로 줄이는가.
- UI, 색, typography, 레이아웃, interaction flow, 정상 animation parameter를 바꾸지 않는가.
- backend URL과 payload가 바뀌어도 기존 endpoint resolver/decoder 경계 안에서 대응 가능한가.
- 원인과 수정 효과를 test 또는 runtime log로 다시 확인할 수 있는가.

## 최종 결정
Sound Constellation의 선행 활성화 margin을 `700px`에서 `0px`로 좁히고, SVG path의 시작 상태를 완전하게 만든다. GLB는 잔여 위험으로 기록하되 시각 동일성을 검증할 브라우저 trace/스크린샷 환경이 생기기 전에는 load timing이나 binary를 변경하지 않는다.

## 해결 방식
1. `SOUND_CONSTELLATION_API_ROOT_MARGIN = '0px'`를 별도 motion model에 두고 viewport 진입 시점에만 API가 활성화되도록 했다.
2. `getRegionPathMotion()`을 추가해 selected/unselected/no-selection 상태 모두 `fill`, `fillOpacity`, `filter`를 반환하게 했다.
3. 각 `<motion.path>`의 `initial`과 `animate`에 완전한 상태를 전달했다. hover/selection transition 설정은 기존 값을 유지했다.
4. unit test로 root margin과 모든 path 상태에 undefined 값이 없음을 고정했다.
5. 개발 서버 HMR 뒤 `/odii` 응답이 `86ms`, 이후 `17ms`였고 반복 Motion 경고 및 첫 viewport의 즉시 `/api/odii` 요청이 사라진 것을 log로 확인했다.

## 결과
- `npx vitest run`: 22 files, 72 tests passed.
- `npx tsc --noEmit --pretty false`: passed.
- `npm run build`: passed.
- target lint에는 새 error가 없고 기존 external `<img>` warning만 남았다.
- UI/색/typography/flow/정상 motion parameter는 변경하지 않았다.
- 잔여 검증: 실제 브라우저에서 landing→Odii cold navigation Performance trace를 수집해 GLB parse task와 Odii first scroll frame time을 비교한다. GLB가 유의미한 long task로 확인될 때만 model compression 또는 route-aware activation을 별도 visual regression과 함께 진행한다.
