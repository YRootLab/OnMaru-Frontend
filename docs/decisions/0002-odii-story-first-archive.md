# Odii 아카이브는 이야기 우선 페이지네이션과 선택적 장소 묶어 보기를 사용한다

## 맥락 및 문제 설명

한국관광공사 Odii API의 목록 기본 단위는 `stid`를 가진 개별 오디오 이야기다. 전체 결과가 수천 건이 될 수 있으며, 같은 관광지의 여러 해설이 별도 레코드로 반환된다. 지도 섹션은 지역·좌표·장소를 중심으로 탐색하므로, 아카이브까지 장소 중심으로 전면 집계하면 탐색 역할이 중복된다. 전체 데이터를 미리 가져와 프런트에서 집계하면 초기 요청·이미지·메모리 비용도 커진다.

## 검토한 대안

* 단일 열의 개별 이야기 목록을 유지한다.
* 모든 응답을 장소별로 전면 집계해 장소 중심 아카이브를 만든다.
* 이야기 단위 페이지네이션을 기본으로 하고, 현재 검색 결과에서만 파생 `placeKey`로 장소별 묶어 보기를 제공한다.

## 결정 결과

선택한 대안: **이야기 단위 페이지네이션을 기본으로 하고, 현재 검색 결과에서만 파생 `placeKey`로 장소별 묶어 보기를 제공한다**, 그 이유는 Odii 원본 데이터 단위를 보존하면서 지도 섹션과의 역할 중복 및 전체 사전 적재를 피할 수 있기 때문이다.

## 구현 제약

* 기본 아카이브 요청은 `getStoryPage`를 통해서만 수행하고, 한 요청에서 전체 결과를 가져오지 않는다.
* 장소 묶음은 원본 API의 공식 장소 ID가 아닌 제목의 장소 접두어와 보조 위치 정보를 이용해 현재 페이지 범위에서만 만든다.
* 장소 묶음의 개수는 전체 관광지 수로 표시하지 않는다.
* 실제 장소 고유 ID가 API에 추가되면 파생 `placeKey`보다 해당 ID를 우선한다.

## 결과 및 영향

* 장점: 수천 개 이야기를 조밀하게 탐색하고, 검색·카테고리·페이지네이션을 원본 API와 일관되게 유지한다.
* 장점: 지도는 장소 탐색, 아카이브는 이야기 탐색이라는 역할이 분명해진다.
* 단점: 서로 다른 페이지에 걸친 같은 장소의 모든 이야기를 한 번에 완전하게 묶지는 않는다.
* 단점: 제목이 불규칙한 데이터는 단일 이야기로 남을 수 있다.

## 확인 방법

* [ ] `getStoryPage`의 `totalCount`, `pageNo`, `numOfRows`로 아카이브 페이지를 구성한다.
* [ ] 장소별 묶어 보기는 현재 페이지의 이야기만 집계하며, 원본 `stid`를 잃지 않는다.
* [ ] 전체 결과나 전체 이미지를 아카이브 최초 진입에서 선로딩하지 않는다.

## 재검토 조건

* Odii API가 안정적인 관광지 고유 ID 또는 장소별 이야기 조회 엔드포인트를 제공한다.
* 백엔드 검색 인덱스가 장소 단위 집계를 원본 데이터와 동기화해 제공한다.
