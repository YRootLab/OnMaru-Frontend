# Odii 자연어 안내는 출처 강제 RAG 백엔드와 LangGraph 라우팅을 사용한다

## 맥락 및 문제 설명

Odii 원본 API는 개별 이야기의 제목, 대본, 카테고리, 좌표, 재생시간을 제공하지만 사용자는 ‘경주에서 10분 안에 들을 수 있는 왕릉 이야기’처럼 자연어로 탐색할 수 있어야 한다. 프런트엔드가 모델 키나 검색 인덱스를 직접 보유하면 비밀 관리, 최신 데이터 동기화, 평가, 속도 제어가 불가능하다. 반대로 모델만 호출하면 Odii 데이터 밖의 답변을 만들어 출처와 신뢰를 잃을 수 있다.

## 검토한 대안

* 프런트엔드 키워드 필터만 유지한다.
* 프런트엔드에서 LLM과 벡터 검색을 직접 호출한다.
* 백엔드 RAG 서비스가 Odii 인덱스를 검색하고, LangGraph가 질의 유형별 도구를 제한적으로 라우팅하며, 프런트엔드는 동일 출처를 가진 응답만 표시한다.

## 결정 결과

선택한 대안: **백엔드 RAG 서비스가 Odii 인덱스를 검색하고, LangGraph가 질의 유형별 도구를 제한적으로 라우팅하며, 프런트엔드는 동일 출처를 가진 응답만 표시한다**, 그 이유는 원본 데이터 갱신·키 보안·검색 품질 평가를 서버에서 통제하고, 답변을 재생 가능한 Odii 이야기로 검증할 수 있기 때문이다.

## 구현 제약

* 브라우저는 `/api/odii/ask`만 호출하며 모델 공급자 키, 벡터 DB 자격 증명, LangGraph 내부 상태를 받지 않는다.
* 백엔드는 Odii `stid`를 기본 문서 식별자로 사용하고 제목·대본·카테고리·좌표·재생시간을 메타데이터로 인덱싱한다.
* 검색은 카테고리·지역·재생시간 메타데이터 필터와 키워드/벡터 하이브리드 검색을 함께 사용한다.
* 답변에는 최소 하나 이상의 Odii `stid` 출처가 있어야 하며, 출처가 없으면 답변 대신 검색 실패 상태를 반환한다.
* LangGraph는 직접 검색, 조건 검색, 다단계 질의에만 제한된 도구 라우팅을 사용하며 임의의 외부 도구 호출을 허용하지 않는다.
* 백엔드는 요청 길이 제한, 사용자별 rate limit, 프롬프트 인젝션 방어, 추적 ID, 검색 품질 평가 세트를 갖춘다.

## 결과 및 영향

* 장점: 사용자는 자연어 질문으로 실제 재생 가능한 Odii 이야기를 찾을 수 있고, 화면은 근거를 직접 제시한다.
* 장점: 모델 비용·캐시·평가·보안 정책을 프런트와 독립적으로 운영할 수 있다.
* 단점: 인덱스 동기화, 임베딩 비용, 평가와 관측성 운영이 추가된다.
* 단점: RAG 백엔드가 구성되기 전 질문 UI는 명확한 준비 상태를 보여야 하며, 임의의 답변을 생성해서는 안 된다.

## 확인 방법

* [ ] `/api/odii/ask`는 구성된 백엔드 URL로만 요청을 프록시한다.
* [ ] 성공 응답에는 답변과 하나 이상의 `stid` 출처가 포함된다.
* [ ] 출처가 없거나 서비스가 구성되지 않았을 때 UI는 사실을 꾸며내지 않고 안내 상태를 표시한다.
* [ ] 회귀 평가 세트에서 추천된 `stid`가 필터 조건과 일치하는지 측정한다.

## 재검토 조건

* Odii API가 자연어 질의와 출처가 검증된 추천 기능을 직접 제공한다.
* 검색 평가에서 하이브리드 RAG보다 단순 메타데이터 검색이 동일 품질·낮은 비용으로 확인된다.
